# Porting the PostgreSQL side to the Rust engine

Status: plan, nothing ported yet. `@payloadcms/db-postgres` (over `packages/drizzle/src/postgres`,
drizzle-orm 0.45.2 `node-postgres` driver, `pg` 8.20.0) runs the upstream TS code with every
`PAYLOAD_ENGINE` value. With `PAYLOAD_ENGINE=rs` the Rust **core** engine (operations, hooks,
validation) already runs on top of it, because the core dispatch does not depend on the adapter.

Infrastructure and reference numbers:

- Server, harness, runner: `test/__rs/pg-harness/README.md` (local PostgreSQL 17 + PostGIS +
  pgvector on :5433, alias vitest config, one database per file, child-process redirection).
- TS baseline per test: `.rs-baseline/postgres-all.json`, summary and failure causes:
  `.rs-baseline/postgres-summary.md`.

The goal is the same as for SQLite (`RUST_PORT.md`, `packages/engine-rs/ENGINE_CONTRACT.md`): every
`payload.db.*` data method of the postgres adapter runs in Rust, with SQL text, params, results,
errors and database state identical to the TS adapter, and no user-facing API change.

## 2. Postgres dialect differences in drizzle 0.45.2 (what the Rust renderer must reproduce)

From `drizzle-orm/pg-core/dialect.js`, `pg-core/columns/*`, `node-postgres/session.js` and
`packages/drizzle/src/postgres/**`:

- **Placeholders**: `escapeParam(num) = '$' + (num + 1)`, numbered in chunk render order (SQLite:
  `?`). Identifiers `"x"` with `"` doubled, strings `'x'` with `'` doubled (same as SQLite).
- **Table references**: `"schema"."table"` when the table has a schema (`schemaName`), aliases
  `"table" "alias"`. Joins can be `left join lateral`.
- **Insert**: `insert into "t" ("a", "b") values ($1, default), (…) [on conflict ("id") do
  update set "a" = $n] returning "id", "a", …`. A column without value (`undefined` or a
  `Param` holding `undefined`): the `$defaultFn()` result as a param (or SQL), else the
  `$onUpdateFn()` result when the column has no static default, else the `default` keyword, so
  static defaults are applied by the server (`PgDialect.buildInsertQuery`). SQLite inlines a
  static `default` as a param first, then `$defaultFn`, `$onUpdateFn`, else `null`. `returning`
  lists every column plainly (no SQLite `cast`).
- **Select**: `select [distinct] … from … where … group by … order by … limit $n offset $n`;
  `limit` rendered when it is a number `>= 0` or an SQL object, `offset` when truthy (same rule as
  SQLite, different placeholder). `count()` is `count(*)` mapped with `Number`.
- **Operators**: `ilike` / `not ilike` for Payload's `like`, `contains` and `not_like`;
  `inArray(col, [])` / `notInArray(col, [])` render `false` / `true` (verified in 0.45.2),
  non-empty lists `in ($1, $2)`. Raw JS arrays inside `sql` templates render `($1, $2)`.
- **JSON**: columns are `jsonb`; `createJSONQuery` (postgres) uses `jsonb_path_exists`; `json_agg`,
  `json_build_object`, `json_build_array`, `jsonb_agg`, casts `'[]'::json` / `'[]'::jsonb`,
  `::text` on the polymorphic relationship value.
- **uuid**: `PgUUID` columns, values are strings both ways; `defaultRandom()` →
  `gen_random_uuid()` server default (insert renders `default`); `uuidv7` via `$defaultFn`.
- **Geometry / PostGIS**: `geometry(Point)` custom column (`toDriver`: `SRID=4326;point(x y)`,
  `fromDriver`: `parseEWKB(hex)`), writes through `ST_GeomFromGeoJSON($n)` (JSON string param),
  reads through `ST_AsGeoJSON("col")::jsonb` extras, `near` / `within` / `intersects` constraints
  and the `<->` raw sort above. Needs the `postgis` extension (`adapter.extensions`).
- **Vector**: `vector`, `halfvec`, `sparsevec`, `bit` raw columns (added by users through
  `rawTables` / `beforeSchemaInit`, test/database/postgres-vector.int.spec.ts), drizzle vector
  column classes (`[1,2,3]` text ↔ number arrays). Requires the `vector` extension.
- **Enums**: select / radio fields and `_locale` columns are `pgEnum`s (`enum_<table>_<field>`,
  `enum__locales`, in `schemaName` when set). For DML they are plain strings (no casts are
  rendered); enum names only matter for DDL, which stays TS.
- **numeric**: number fields are `numeric` with `mode: 'number'`: params `String(value)`, results
  arrive as strings and are decoded with `Number(value)`. Serial / integer ids are int4 (numbers).
- **timestamps**: `timestamp(3) with time zone`, `mode: 'string'`: params are passed as given
  (Payload passes ISO strings), results are the server's text format (drizzle disables pg-types'
  parsers for timestamptz, timestamp, date, interval and their arrays, types 1182/1185/1187/1115/
  1231), then Payload's read transform does `new Date(text).toISOString()`.
- **Arrays**: Payload does not use pg array columns (hasMany values live in `_texts` / `_numbers`
  / `_rels` / select tables). Arrays only appear through custom columns and node-postgres'
  conversion of JS array params into array literals.
- **Returning / affected rows**: every write returns rows through `returning`; `delete` /
  `update` without returning give `rowCount` only (unused by Payload).
- **Error shape**: drizzle wraps driver errors in `DrizzleQueryError(query, params, cause)`; the
  cause is a `pg` `DatabaseError` (`code`, `detail`, `constraint`, `table`, `column`, `schema`,
  `severity`, `routine`, `position`, …). Unique violations are `23505`.
- **Transactions**: `NodePgSession.transaction`: a pool client is checked out, `begin [isolation
  level …] [read only] [deferrable]` (from `transactionOptions`), nested transactions as
  `savepoint sp<n>`, `commit` / `rollback`, client released. Payload "lifts" the callback so a
  transaction spans several adapter calls (`beginTransaction.ts`).
- **Simple vs extended protocol**: node-postgres uses the simple query protocol when a query has
  no params (several statements allowed, e.g. `execute({ raw })`), the extended protocol with an
  unnamed statement otherwise. Results are always in text format and parsed by pg-types.

## 3. Client choice: keep node-postgres via host ops (recommended) vs a Rust driver

### Option A (recommended, stage 1): Rust builds statements, node-postgres executes them

Like the Mongo engine (`MONGO_ENGINE_CONTRACT.md`, "I/O stays on the JS mongoose models"): Rust
produces `{ text, params, mode }` per statement; the TS host executes it on the drizzle session the
TS method would have used, on the JS thread, and returns the rows as drizzle got them. Reasons:

- **Type parsers.** node-postgres results are produced by pg-types plus drizzle's per-query
  overrides (timestamps raw), and by any **global** parser the application registered
  (`pg.types.setTypeParser(...)`, also through a custom `args.pg` module). Only the JS client sees
  those. Int8 / numeric come back as strings, json / jsonb through V8 `JSON.parse` (precision,
  `__proto__` keys, duplicate keys), bytea as `Buffer`, unknown OIDs (geometry, vector) as text.
- **Param conversion.** `pg`'s `prepareValue`: `Date` → local-time string with the process
  time-zone offset (or UTC with `parseInputDatesAsUTC`), `Buffer` → bytea, arrays → array
  literals, objects → `JSON.stringify` (with `toPostgres` support), booleans → `'true'`/`'false'`.
  A Rust driver would have to re-implement all of this, including the V8 date formatting.
- **Transactions.** `beginTransaction` holds a checked-out JS `PoolClient` inside a pending drizzle
  `transaction()` callback; `payload.db.drizzle`, `payload.db.pool`, `payload.db.execute` and user
  code run statements on the same connections. A second (Rust) connection pool cannot join those
  transactions; executing through the session keeps a single connection model, as `payload-sqlite`
  does for SQLite.
- **Pool and options.** `poolOptions` (`max`, `idleTimeoutMillis`, `ssl`, `connectionString`,
  `application_name`, statement timeouts, `onConnect`), `pool.on('error')` reconnect logic
  (`connect.ts`), `disableCreateDatabase` / `createDatabase`, custom `pg` modules, and
  `@payloadcms/db-vercel-postgres` (`@vercel/postgres` / Neon client over the same drizzle code)
  all keep working unchanged.
- **Read replicas.** `withReplicas` routes `select` / relational queries to a random replica
  (`Math.random()`), writes, `execute` and transactions to the primary; Payload adds
  `primaryDrizzle` / `getPrimaryDb` / read-after-write routing (`readReplicasAfterWriteInterval`,
  `lastWriteTimestamp`). The host op names the drizzle entry point the TS code used (`select`,
  `selectDistinct`, `query` (relational), `insert`, `update`, `delete`, `execute`) and the db
  object it was called on (session db, `primaryDrizzle`), so TS makes the same routing decision
  and consumes `Math.random()` in the same order.
- **Logging, errors, spies.** Executing through drizzle's `session.prepareQuery({ sql, params },
  fields, name, isResponseInArrayMode = true).execute()` keeps `adapter.logger` (`logger: true`
  logs every query), drizzle's `queryWithCache` wrapping into `DrizzleQueryError` with the
  original `DatabaseError` as `cause` (returned to TS as a host object, as the Mongo engine does),
  and user spies on `payload.db.drizzle` / `pool.query`.
- **Cost.** One JS round trip per statement is negligible next to a network round trip, and the
  engine code stays synchronous: `payload-sql-engine`'s `stepped` method thread already stops after
  every statement; for postgres the step hands the statement to JS and resumes with its rows
  (or its error) when the JS promise settles. The `Executor` / `Statements` traits of
  payload-sql-find / payload-sql-upsert stay synchronous. TS awaits every drizzle statement and
  postgres I/O completes in a later macrotask, so the step boundaries match the TS awaits; there is
  no libsql-style synchronous execution to reproduce.

What crosses the boundary per statement: `{ text, params (tree-encoded driver values, after the
column's mapToDriverValue), entry, db }` → rows as tree-encoded arrays (array mode), or a host-object
error. Typed values: `$date` (a `Date` param reaches `prepareValue` as a `Date`), `$bigint`,
`$buffer` (bytea), `$undefined`. Rust decodes rows with the drizzle pg column classes.

### Option B (stage 2, only after option A parity): tokio-postgres / sqlx in Rust

Gains: no JS round trip, binary protocol, prepared statement cache. Fidelity costs, all of which
would need exact ports and differential tests:

- pg-types text parsing (int8 / numeric strings, `JSON.parse` semantics, `bool`, arrays of every
  type, bytea hex, unknown OIDs as text) and drizzle's per-query overrides; global user parsers
  are lost (behaviour change for users who register them).
- `prepareValue` param conversion, incl. `Date` with the process TZ, `toPostgres`, nested arrays.
- Error objects: `DatabaseError` fields and messages (`error: duplicate key value violates unique
  constraint "…"`, `detail`, `constraint`) as node-postgres builds them from the ErrorResponse.
- Transactions shared with `payload.db.drizzle` / `pool` would need the Rust pool to back the JS
  drizzle instance (a JS `pg`-compatible client implemented over Rust, as `@payloadcms/engine-rs/
  sqlite`'s `createClient` does for libsql), including pool semantics (`max`, queueing,
  `idleTimeoutMillis`, `connect` events) and `pg.Pool` subclass identity (`adapter.pool` is
  user-facing).
- Read replicas, `ssl` options, `application_name`, Neon / Vercel clients (`db-vercel-postgres`)
  would need Rust equivalents or keep option A.
- tokio runtime inside the addon (the SQLite and Mongo engines have none today).

Recommendation: option A for the port; revisit B only for performance with a measured gain.

## 5. Risks and open questions

- **Relational query builder size.** `PgDialect.buildRelationalQueryWithoutPK` differs
  structurally from the SQLite builder (lateral joins, alias naming, `order by` inside `json_agg`,
  limit handling inside lateral subqueries). It is the largest new piece.
- **Timestamp formats.** Top-level values (server text format, `DateStyle`/`TimeZone` dependent)
  vs nested JSON values (ISO 8601). The server's `TimeZone` setting changes the text (`+00` vs
  `+01`); the harness pins UTC like upstream's docker image, the port must not assume it.
- **Collation.** Sorting text depends on the database collation (glibc `en_US.utf8` on the
  upstream image, ICU `en-US` here); not an engine concern but it affects baseline comparisons
  across machines.
- **`numeric` precision.** `numeric` → string → `Number()` loses precision beyond 2^53 exactly as
  TS does; nested JSON numerics go through `JSON.parse`. Rust must use the same conversions
  (V8 number parsing) in both places.
- **Microtask ordering.** With async I/O, concurrent adapter calls interleave by I/O completion
  (non-deterministic in TS too). Statement order within one call is deterministic and must match.
- **Read replica runs** need a streaming replica on :5434 (`test/__helpers/shared/db/postgres/
  replica-entrypoint.sh`). Without docker this needs a second nix PostgreSQL started with
  `pg_basebackup -R` from the primary (`wal_level=replica`, `max_wal_senders`); not set up yet.
- **Migrations, push, `generateSchema`, `createDatabase`, `dropDatabase`, `createExtensions`**
  stay TS (drizzle-kit), as for SQLite.
